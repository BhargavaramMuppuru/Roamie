ROAMIE BACKEND - TECHNICAL IMPLEMENTATION DOCUMENT
Version: 1.0
Date: 2026-05-05

============================================================
1) EXECUTIVE TECHNICAL SUMMARY
============================================================
Roamie is a TypeScript/Node.js backend that turns chat threads into a full
group-trip operating system. It combines:

1. Deterministic workflow orchestration (state machine + ledger rules)
2. AI-assisted understanding/content generation (OpenAI services)
3. Messaging platform integration (Linq webhook + outbound messaging)

The system supports end-to-end trip lifecycle execution:
- trip creation
- attendance confirmation
- planning (hotels/food/activities)
- polling and final selection
- itinerary shaping
- expense logging and split management
- partial/full settlement
- trip closure and memory recap

Core design principle:
"Deterministic for money/workflow correctness, AI for language flexibility."

============================================================
4) DOMAIN MODEL (CONCEPTUAL)
============================================================
Important entities and responsibilities:

- Trip:
  Root lifecycle object for one chat thread (or created group thread).
  Stores state, destination, dates, budget, and itinerary-related fields.

- Participant:
  User membership in a trip. Includes RSVP state, display name enrichment,
  phone mapping, subgroup tag, and arrival notes.

- Expense:
  A payment event (who paid, how much, what for).

- ExpenseSplit:
  Per-user liability lines for an expense (shareAmount, paidAmount, settled).

- SplitPayment (+ allocations):
  Audit trail for partial/full payments across split rows.

- SettlementRecord:
  Rebuilt net transfer recommendations ("who should pay whom").

- MessageContext:
  Tracks outbound messages requiring reaction-driven behavior
  (attendance confirmations, payment confirmations, etc.).


============================================================
5) STATE MACHINE AND LIFECYCLE IMPLEMENTATION
============================================================
Trip states:
- INIT
- ATTENDANCE
- PLANNING
- ITINERARY
- ACTIVE
- SETTLEMENT
- CLOSED

State machine goals:
1) Ensure predictable business behavior by state.
2) Allow natural-language flexibility without violating lifecycle invariants.
3) Route the same intent differently depending on state.

Examples:
- REQUEST_HOTELS during ATTENDANCE can move trip into PLANNING.
- START_TRIP transitions toward ACTIVE.
- REQUEST_SETTLEMENT/paid cues move flow into SETTLEMENT.
- CLOSE_TRIP finalizes and emits closure summary.

Why this design:
- Chat interactions are messy and asynchronous.
- Explicit state boundaries prevent accidental feature misuse.
- Maintains consistent user experience for group coordination.


============================================================
6) INTENT UNDERSTANDING (HOW IT WORKS)
============================================================
Hybrid intent architecture:

Layer A - Rule-based parser:
- Fast regex/heuristic matching for common intents and shortcuts.
- Handles robust patterns for:
  attendance yes/no,
  weather/hotel/food/activity requests,
  split history/my splits,
  mark paid,
  poll finalize,
  display name/contact roster,
  expense line patterns and mutations.

Layer B - OpenAI intent parser:
- Used for broader natural language coverage and structured extraction.
- Returns typed intent payload with optional fields.

Fallback strategy:
- If AI parse fails, system falls back to rules.
- Unknown intents can produce contextual AI responses.

Why hybrid:
- Rules are deterministic and low-latency for critical commands.
- AI handles high language variance and natural phrasing.
- Combined approach improves reliability + UX.


============================================================
7) GROUP CHAT GATING AND TRIGGER LOGIC
============================================================
Default behavior in groups:
- Messages without "Roamie" are ignored to prevent noisy auto-replies.

Intentional exceptions:
- Bare poll votes: "1", "2", "3"
- Attendance quick confirmations/declines in attendance context
- Attachment/voice-driven processing in active trip contexts

Recent implemented behavior:
- Mention can appear anywhere in text (not only prefix).
- Voice/image messages can be processed without saying "Roamie"
  when trip is active and not closed.

Why:
- Keeps normal human conversation uninterrupted.
- Preserves low-friction workflows for voting and media-based inputs.

============================================================
11) EXPENSE ENGINE AND SPLIT LOGIC
============================================================
Expense capture supports:
- amount-first or description-first patterns
- named split targets ("for Sam and Jordan")
- explicit custom amounts ("Sam $7 Jordan $13")
- split bonuses (extra amount for one participant)
- subgroup-labeled expenses
- receipt-assisted expense extraction

Critical payer rule:
- Payer is excluded from owed split targets.
- Implemented across equal splits, named splits, subgroup fallback,
  and settlement/history calculations.

Why:
- Avoids self-owing math artifacts.
- Keeps liabilities aligned with real reimbursement expectations.


============================================================
12) RECEIPT AND VOICE INPUT PIPELINE
============================================================
Receipt parsing:
- Triggered by image attachments when enabled.
- Best-effort extraction of amount + merchant cues.
- Can promote UNKNOWN intent into ADD_EXPENSE.

Voice parsing:
- Audio attachment URL transcribed via OpenAI transcription model.
- Transcript merged into inbound text for normal intent flow.

Recent UX upgrade:
- No mandatory "Roamie" keyword for voice/image in trip context.

Why:
- Media inputs are common in real group travel operations.
- Eliminates friction for expense logging in the field.


============================================================
13) BUDGET TRACKING
============================================================
Budget features:
- Trip budget captured at creation/update.
- Expense follow-up includes budget pulse (spent vs budget).
- Threshold crossing warning (default via BUDGET_WARNING_PERCENT).
- Over-budget messaging.
- Scheduler-driven reminders for budget status.

Why:
- Continuous budget visibility reduces end-of-trip surprises.


============================================================
14) SETTLEMENT, PAYMENTS, AND HISTORY
============================================================
Settlement:
- Rebuilds net transfer records from outstanding split liabilities.
- Output: minimal transfer set ("Who should pay whom").

Payment support:
- Partial payment command parsing and allocation.
- Mark-paid prompts and reaction shortcut flow.
- splitPayment audit records retained.

History views:
- Group split history:
  expense -> share/paid/still owed + payment events
- Personal split history:
  user-specific dues + total outstanding

Correctness safeguards implemented:
- Ignore payer-self split rows for settlement and history.
- Settlement netting based on non-self still-owed lines.

Why:
- Finance paths must be deterministic, auditable, and user-trustworthy.

============================================================
22) WHY THIS ARCHITECTURE IS STRONG
============================================================
1) Correctness where it matters:
   Money, settlement, and state transitions are deterministic.

2) Flexibility where users expect it:
   AI handles natural language variation and content generation.

3) Chat-native operation:
   Minimal command burden, reaction shortcuts, media support.

4) Production-minded controls:
   validation, rate limits, logs, idempotent patterns, scheduled nudges.

5) Evolvable service boundaries:
   clear modules for intents, state machine, ledger, settlement, and AI.
